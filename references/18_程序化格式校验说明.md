# 18 · 程序化格式校验说明（防幻觉的最终闸门）

> **2026-08-27 迭代**：校验器升 v2，追加 11 元话语黑名单 / 12 正文加粗计数 / 13 附录代码完整性 三项（规则与自测见 `20_2025C题获奖卷对标与雷点库.md` §七）。
> 用户铁律：**改完格式必须用程序化校验逐条核验成品文件，不允许凭记忆汇报。**
> 本文件说明 `validate_docx_format.py` 的用途、读法、与流程的接合点。

---

## 为什么必须程序化
"我觉得格式没问题"在国赛里最危险——低级版式错误（字体错、三线表漏边框、漏封面表、有目录）会让评委先入为主"不严谨"。人眼逐条查 44 页极易漏，脚本逐条查 0 漏。

## 怎么用
```bash
# ⑥ 交付前、⑤ 评审后，对成品 docx 跑：
python validate_docx_format.py <论文.docx> --json check.json
```
- 输出每条约：`[PASS/WARN/FAIL] 检查项  实测细节`
- 汇总：`{"pass":N,"warn":M,"fail":K,"grade":"..."}`
- `check.json` 存完整报告，逐条整改时对照。

## 10 项检查（对照 17_规范）
1. 页面 A4（21×29.7cm）
2. 页边距 左右≈2.70 / 上下≈2.54cm
3. 无目录（TOC）
4. 含「摘要」与「关键词」
5. 问题驱动分章（问题N 模型的建立与求解，≥2）
6. 含「模型的评价与推广/改进」
7. 正文 小四 12pt±0.3 黑色（v3 更正，旧“五号”作废）
8. 一级标题 黑体
9. 二级标题 黑体
10. 三线表（无竖线、上下粗线）
11. 图表标题样式存在且连续编号
12. 参考文献 `[n]` 编号格式
13. 无封面信息表（v3 反转：C050 首页直接题名+摘要，出现信息表=FAIL）

### v2 追加三项（2026-08-27，规则词表见 `20` 号）
14. 元话语/工程黑话黑名单（如实/口径/引擎/判据/契约/预案/降级/重放/主力/基线A/B/MC模拟…）→ WARN
15. 正文加粗检查（2026-09-05 更新为 v3 口径，旧"≤3 处"已废）：摘要页加粗字符 <200 → WARN；正文非标题加粗片段 <10 或 >400 → WARN；整段全加粗 → 违规（对齐 17 号 §2A 克制加粗范式，规则常量在 validate_docx_format.py 顶部）
16. 附录完整性：无 ≥30 行连续代码样式段落且无 import/def/function 等特征行 → FAIL（附录代码缺失）

### v3/v4 追加（详见脚本头部变更记录）
- 正文主字号 小四12pt±0.3（违例 FAIL）、题名/『摘 要』黑体三号居中、无封面信息表（C050 范式）
- "AI 工具使用声明"缺声明 = FAIL（2026 官方新规），声明排在参考文献之后 = WARN

## 验收标准
- **fail 必须 == 0**，否则阻断定稿，逐条改完再评。
- **warn 仅允许**：封面/图表类（首轮未嵌图时图题为 0 属正常）、文献不足 8 条（写作中）、加粗密度类（写作过程中允许，⑥ 交付前必须清零达标）。其余 warn 必须清零。
- 每条 `detail` 即整改点，照着改，不靠"感觉"。

## 与 build_docx.py 的衔接
`build_docx.py` 生成的 .docx 已套 `17` 规范（含三线表程序化加边框、封面全框表、图题下/表题上），故跑校验器通常直接 PASS；若从 Word 手动粘贴内容，则更需本校验器兜底抓"字体/边框/目录"类问题。
